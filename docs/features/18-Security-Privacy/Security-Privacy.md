# فیچر: Security & Privacy (امنیت و حریم خصوصی)

## توضیح کلی

این فیچر تمام مکانیزم‌های امنیتی و حریم خصوصی نرم‌افزار را مدیریت می‌کند. 
هدف اصلی جلوگیری از دسترسی غیرمجاز به داده‌های مالی و جلوگیری از سوءاستفاده از اطلاعات کاربر است.

---

## User Stories

### Must Have
- قفل اپ (FaceID، TouchID یا PIN)
- احراز هویت رمز عبور اولیه
- مدیریت جلسات کاربری (ورود/خروج امن)
- رمزنگاری داده‌های حساس در دیتابیس
- جلوگیری از کپی داده‌ها (کپی‌پیست محدود)

### Should Have
- ورود چندمرحله‌ای (MFA)
- مدیریت دستگاه‌ها (لیست دستگاه‌های مجاز)
- قفل دوره‌ای (timeout و قفل خودکار)
- لاگ فعالیت‌های امنیتی (بازبینی امنیتی / security audit)
- پشتیبانی از Secure Enclave (در دستگاه‌های پشتیبانی شده)

---

## Business Rules

1. تمام داده‌های مالی با رمزنگاری **در سطح فایل SQLite** (Blob کامل) حفظ می‌شوند — قبل از سریالایز در IndexedDB رمزنگاری می‌شوند و بعد از خواندن از IndexedDB رمزگشایی و به sql.js تحویل داده می‌شوند.
2. قفل اپ باید بعد از هر اجرای اپ یا پریود خالی کاربر فعال شود.
3. تعداد تلاش ناموفق برای قفل اپ محدود است (مثلاً ۵ بار).
4. **پس از عبور از حداکثر تلاش ناموفق (`maxFailedAttempts`)، اپ صرفاً برای یک بازه زمانی افزایشی (Exponential Backoff — مثلاً ۳۰ ثانیه، سپس ۱ دقیقه، سپس ۵ دقیقه و...) قفل می‌شود؛ در هیچ شرایطی داده‌ها پاک نمی‌شوند.** چون این یک اپ آفلاین محلی است و تنها نسخه داده‌های مالی چندساله کاربر همان دیتابیس روی همین دستگاه است (طبق `db.md`، پشتیبان‌گیری صرفاً یادآوری می‌شود، نه اجباری و تأییدشده)، پاک‌سازی خودکار می‌تواند باعث از‌دست‌رفتن غیرقابل‌جبران کل تاریخچه حسابداری/سرمایه‌گذاری شود — که مستقیماً با اصل «هیچ داده‌ای نباید از بین برود» در تضاد است. اگر کاربر واقعاً رمز/PIN را فراموش کند، مسیر بازیابی همان «بازیابی از آخرین فایل Export» است (طبق `db.md`)، نه پاک‌سازی خودکار توسط اپ.
5. رمز عبور یا PIN هرگز در حافظه یا لوگ ذخیره نشوند - فقط هش ذخیره شود.
6. کپی‌پیست از فیلدهای حساس (مانند شماره حساب، شناسه) محدود شود.
7. تغییر رمز عبور یا PIN باید با تأیید هویت فعلی صورت گیرد.
8. فعال کردن قفل باید باعث قفل شدن فوری شود.

## Domain Entities

### ۱. Security Settings (جدول: `sec_settings`)

- `id` → UUID یا کلید ثابت
- `lockEnabled` → boolean (آیا قفل اپ فعال است؟)
- `lockTimeoutMinutes` → number (مدت زمان تا قفل خودکار)
- `maxFailedAttempts` → number (حداکثر تلاش ناموفق قبل از فعال‌شدن Backoff — **نه پاک‌سازی**)
- `biometricEnabled` → boolean (آیا FaceID/TouchID مجاز است؟)
- `pinEnabled` → boolean (آیا PIN مجاز است؟)
- `pinHash` → string (nullable — هش PIN با PBKDF2/bcrypt؛ فقط وقتی `pinEnabled=true` پر می‌شود)
- `pinSalt` → string (nullable — نمک تصادفی؛ اگر bcrypt استفاده شود salt داخلی الگوریتم کافی است)
- `hasBackup` → boolean (آیا کاربر پشتیبان تهیه کرده؟)
- `createdAt` → datetime
- `updatedAt` → datetime

### ۲. Session Log (جدول: `sec_session_logs`) — Should Have

- `id` → UUID
- `type` → string (`login`, `logout`, `locked`, `unlocked`, `failed_attempt`)
- `timestamp` → datetime
- `success` → boolean

## APIهای داخلی

### Security APIs
- `getSecuritySettings` → دریافت تنظیمات امنیتی
- `updateSecuritySettings(data)` → بروزرسانی تنظیمات
- `enableLock(type, credential)` → فعال‌سازی قفل با FaceID/TouchID یا PIN
- `disableLock` → غیرفعال‌سازی قفل
- `verifyLock(credential)` → تأیید هویت کاربر
- `forceLock` → قفل فوری اپ
- `getFailedAttempts` → دریافت تعداد تلاش‌های ناموفق
- `resetFailedAttempts` → ریست کردن تعداد تلاش‌ها (پس از ورود موفق)
- `getLockoutRemainingSeconds` → ثانیه‌های باقی‌مانده از Backoff فعلی (برای نمایش در UI)

### Encryption APIs
- `encryptData(data, key)` → رمزنگاری **کل Blob فایل SQLite** قبل از نوشتن در IndexedDB (ورودی: `Uint8Array` کل دیتابیس؛ نه رکورد تکی)
- `decryptData(encrypted, key)` → رمزگشایی Blob و تحویل `Uint8Array` به sql.js برای بارگذاری در RAM (نه رمزگشایی فیلد-به-فیلد)
- `generateKey` → تولید کلید رمزنگاری جدید (مشتق از PIN/بیومتریک با Web Crypto API)

### Session APIs
- `createSession` → ایجاد جلسه جدید
- `endSession` → پایان جلسه
- `checkSession` → بررسی وضعیت جلسه
- `extendSession` → تمدید جلسه

## نکات طراحی

- **لایه رمزنگاری**: فایل دیتابیس SQLite **قبل از سریالایز و نوشتن در IndexedDB** (طبق الگوی Write-to-temp-then-swap مستندشده در `db.md`) با کلید مشتق‌شده از PIN/بیومتریک/Secure Enclave رمزنگاری (AES-GCM پیشنهادی) می‌شود. IndexedDB صرفاً حامل یک Blob رمزنگاری‌شده نهایی است — **نه** محل اعمال رمزنگاری فیلد-به-فیلد روی داده‌های ساختاریافته؛ IndexedDB را «یک کانتینر رمزنگاری‌شده» بدانید، نه یک NoSQL با رمزنگاری ستونی. کلید رمزنگاری در صورت پشتیبانی سیستم‌عامل می‌تواند از Secure Enclave/Trusted Execution Environment استفاده کند (Should Have، نه پیش‌نیاز نسخه ۱).
- **پس از حداکثر تلاش ناموفق، فقط قفل موقت با Backoff افزایشی اعمال می‌شود؛ پاک‌سازی خودکار داده‌ها ممنوع است** (طبق قاعده ۴).
- تغییر رمز عبور/PIN باید کلید رمزنگاری را re-encrypt کند.
- در صورت پیاده‌سازی لاگ امنیتی (Should Have)، این لاگ هم باید آفلاین و محلی ذخیره شود.
- برای نسخه ۱، فقط PIN/بیومتریک ساده + رمزنگاری دیتابیس کافی است؛ MFA، مدیریت چندین دستگاه و بازبینی امنیتی کامل به نسخه‌های بعدی موکول می‌شوند تا پیاده‌سازی اولیه ساده و قابل انجام برای هر تیم توسعه بماند.

### API Key سرویس‌های بیرونی

- کلیدهای API قیمت (و مشابه) **جزو اسرار نشست**اند، نه داده مالی ذخیره‌شونده در SQLite.
- نسخه ۱: فقط Session Storage؛ پس از بستن tab کاربر دوباره وارد می‌کند.
- ممنوع: plaintext در LocalStorage، ذخیره در جداول دیتابیس، لاگ کردن مقدار کلید.
- آینده (خارج از v1): Remember رمزنگاری‌شده با Web Crypto و/یا Credential Vault متصل به قفل اپ.
